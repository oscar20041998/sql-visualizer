# Feature Request: Persistent Chat History for Database AI Assistant

## Context

I am developing an AI-powered SQL/database analysis application called **SQL Visualizer**.

The application currently contains a **Database AI Assistant** whose responsibility is to answer database-related questions for these four SQL dialects:

* MySQL
* PostgreSQL
* Microsoft SQL Server
* Oracle

The Database AI Assistant is already working correctly and must NOT have its existing AI/RAG behavior changed.

The current assistant supports:

* Database-related Q&A
* SQL questions
* Schema design questions
* Index questions
* Transaction questions
* Database-specific questions
* RAG-grounded answers using official database documentation when relevant
* Source labels/citations for grounded answers
* Streaming AI responses
* Conversation state while the page/session is active

The current implementation uses Zustand for conversation state.

However, the assistant currently does not have persistent chat history.

For now, I want to persist chat history using **browser localStorage only** because the backend persistence layer has not been implemented yet.

The architecture MUST be designed so that localStorage can later be replaced by a backend/API persistence layer without requiring a major rewrite of the UI or chat business logic.

---

# Primary Goal

Implement a complete **Chat History** experience for the Database AI Assistant.

The user should be able to:

1. Start a new conversation.
2. Automatically save conversations locally.
3. See previous conversations in a history/sidebar panel.
4. Open a previous conversation.
5. Continue chatting in an existing conversation.
6. Rename a conversation.
7. Delete a conversation.
8. Search conversations by title/content.
9. Switch between conversations without losing messages.
10. Persist conversations after page refresh/browser restart.
11. Keep conversations isolated from other application features.

# 3. Design for future backend migration

Do NOT scatter localStorage calls throughout React components.

Create a persistence abstraction.

Preferred conceptual architecture:

```text
Database AI Assistant UI
        |
        v
Conversation / Chat Service
        |
        v
ChatHistoryRepository
        |
        +---- LocalStorageChatHistoryRepository
        |
        +---- Future: ApiChatHistoryRepository
```

The UI and business logic should depend on the repository interface, not directly on localStorage.

For example:

```typescript
interface ChatHistoryRepository {
  getConversations(): Promise<ChatConversation[]>;
  getConversation(id: string): Promise<ChatConversation | null>;
  saveConversation(conversation: ChatConversation): Promise<void>;
  deleteConversation(id: string): Promise<void>;
  renameConversation(id: string, title: string): Promise<void>;
  searchConversations(query: string): Promise<ChatConversation[]>;
  clearAll(): Promise<void>;
}
```

A local implementation can then use:

```typescript
LocalStorageChatHistoryRepository
```

Later we should be able to implement:

```typescript
ApiChatHistoryRepository
```

without changing the Database AI Assistant UI.

# Conversation Data Model

Create a strongly typed conversation model.

Suggested structure:

```typescript
type DatabaseDialect =
  | 'mysql'
  | 'postgresql'
  | 'sqlserver'
  | 'oracle';

interface ChatMessage {
  id: string;

  role: 'user' | 'assistant' | 'system';

  content: string;

  createdAt: string;

  /**
   * Optional metadata generated by the Database AI Assistant.
   */
  metadata?: {
    dialect?: DatabaseDialect;

    sources?: Array<{
      title?: string;
      source?: string;
      url?: string;
    }>;

    grounded?: boolean;

    model?: string;

    provider?: string;
  };
}

interface ChatConversation {
  id: string;

  title: string;

  dialect?: DatabaseDialect;

  messages: ChatMessage[];

  createdAt: string;

  updatedAt: string;

  /**
   * Optional metadata for future backend synchronization.
   */
  version: number;
}
```

Do not over-engineer the model.

The model should contain enough information to support the current UI and future backend persistence.

```typescript

The conversation ID must remain unchanged when:

* renaming
* reopening
* adding messages
* refreshing the page

```

Initial title:

```text
How do I create an index in PostgreSQL?
```

Example:

```text

```

```typescript
generateConversationTitle(firstUserMessage: string): string
```

The user must also be able to rename the conversation manually.

# Automatic Persistence

Every meaningful conversation state change should be persisted.

Persist when:

* a new conversation is created
* user sends a message
* assistant response is completed
* conversation title changes
* conversation is deleted

Avoid writing to localStorage excessively during streaming.

IMPORTANT:

Do NOT persist every streaming token/chunk.

Instead:

```text
User message
    ↓
Persist conversation

Assistant streaming
    ↓
Update in-memory state only

Assistant response completed
    ↓
Persist conversation once
```

This avoids excessive localStorage writes.

---

# Streaming Safety

The Database AI Assistant currently supports streamed responses.

History implementation MUST NOT break streaming.

During streaming:

```text
assistant message
      ↓
stream chunks
      ↓
UI updates
```

Only after the final response has successfully completed:

```text
stream completed
      ↓
persist final assistant message
```

If streaming fails:

* preserve the existing UI error behavior
* do not store an incomplete assistant response unless the existing application explicitly treats it as a valid message
* do not corrupt the previous conversation state

---

# localStorage Schema

Use one centralized key.

Example:

```typescript
const CHAT_HISTORY_STORAGE_KEY =
  'sql-visualizer:database-ai-assistant:chat-history';
```

Do not create one localStorage key per conversation.

Store:

```typescript
ChatConversation[]
```

under the single namespace.

The storage layer must:

1. Parse JSON safely.
2. Validate the loaded structure.
3. Handle corrupted data gracefully.
4. Never crash the application because localStorage contains invalid JSON.
5. Recover using an empty conversation list when necessary.
6. Handle localStorage being unavailable.

---

# Storage Size Protection

localStorage has limited storage capacity.

Do not blindly store unlimited history.

Implement a reasonable safety mechanism.

For example:

```text
Maximum conversations:
100
```

and/or

```text
Maximum stored characters/messages per conversation
```

Do not silently delete important user data.

If a storage limit is reached:

* fail gracefully
* log the error
* keep the current in-memory conversation
* show a non-blocking user notification if appropriate

Do not crash the Database AI Assistant.

---

# Zustand Integration

The existing Zustand conversation state should remain the source of truth for the active conversation UI.

Add a dedicated history state layer rather than replacing the entire existing store.

Conceptually:

```text
Zustand
│
├── activeConversationId
├── conversations
├── messages
│
├── createConversation()
├── switchConversation()
├── addMessage()
├── updateConversation()
├── renameConversation()
├── deleteConversation()
│
└── loadChatHistory()
```

Do not duplicate the same message state in multiple stores unless necessary.

Avoid:

```text
React state
+
Zustand state
+
localStorage state
```

all acting as independent sources of truth.

Recommended model:

```text
localStorage
     ↓
Repository
     ↓
Zustand
     ↓
React UI
```

# Search

Add conversation search.

Search should match:

* conversation title
* user message content
* assistant message content

Example:

```text

```

should find conversations where:

* title contains PostgreSQL
* user asked about PostgreSQL indexes
* assistant explained PostgreSQL indexes

Search should be case-insensitive.

For the current localStorage implementation, a simple in-memory filtering algorithm is sufficient.

Do NOT introduce a vector database or embeddings for chat-history search yet.

# Error Handling

The history feature must be defensive.

Handle:

### localStorage unavailable

Application continues to work in memory.

### Invalid JSON

Ignore corrupted history and initialize an empty history state.

### Invalid conversation structure

Skip invalid entries instead of crashing.

### Storage quota exceeded

Keep current in-memory state and show a non-blocking error.

### Browser privacy mode / restricted storage

Do not break the Database AI Assistant.

---

# Performance

Do not serialize and write the entire history on every keystroke.

Do not persist every streaming token.

Avoid unnecessary React/Zustand re-renders.

For the first implementation, simplicity is more important than premature optimization.

However, isolate persistence logic so it can later be optimized independently.
